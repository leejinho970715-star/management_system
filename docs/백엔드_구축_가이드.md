# Supabase 백엔드 구축 및 운영 연결

이 저장소는 기존 화면 시안과 실제 Supabase 운영 모드를 함께 지원합니다. `app/runtime-config.js`는 새 `management-system` 프로젝트(`aaeydayqpmcqehuymtnc`, 서울)에 연결한 `supabase` 모드입니다. 스키마·API·공개 이벤트 함수 권한 제한 마이그레이션과 `manage-accounts` 서버 함수를 적용했습니다. 최초 관리자 생성·계정 연결과 실제 로그인 검증, 운영 메일 설정은 별도로 완료해야 합니다.

2026-10-15 배포 확인: Vercel·GitHub Pages 모두 실제 프로젝트 공개 연결 설정을 제공합니다. 운영 Auth의 Site URL과 두 배포 주소의 Redirect URLs를 등록했으며, 공개 회원가입·익명 로그인은 끄고 비밀번호 최소 길이를 12자로 설정했습니다. 실제 클라우드 게이트웨이에서 비로그인 업무 RPC/계정 발급 차단과 Edge 함수의 JWT 차단을 확인했습니다. Security Advisor 경고는 0건이며, 새 DB의 미사용 인덱스 안내는 운영 사용량이 없는 상태의 참고 정보입니다. 인증 사용자 생성 이후의 실제 로그인·업무 저장·초대 메일 발송은 아직 확인하지 않았습니다.

## 구성

- PostgreSQL: 27개 업무 테이블, 개인 프로필, 감사 로그, 내부 필드 정의. 회원·구역·교육 과정 등의 연결은 외래 키로, 출결·교육 참석·납부의 업무 키는 유일 인덱스로 보호합니다.
- 업무 자료는 `private` 스키마, 납부는 `finance` 스키마에 분리합니다. 각 행에는 `data` JSONB, 버전, 작성자·작성 시각·변경 시각·삭제 시각이 있습니다. 관계 키와 주요 수치에는 타입이 있는 생성 컬럼·외래 키·인덱스가 적용됩니다. JSONB가 단일 전역 상태 저장소를 대신하는 구조는 아닙니다. 테이블·행 단위로 검증하고 변경합니다.
- Supabase Auth: 이메일/비밀번호 로그인, 세션 갱신, 로그아웃, 비밀번호 재설정·변경. 권한은 사용자가 수정할 수 있는 `user_metadata`에서 읽지 않습니다. DB 계정의 현재 역할·활동 상태와 인증 세션을 확인합니다.
- SQL RPC: 권한별 초기 조회, 행별 등록·수정·삭제·복원, 출결·납부·보고 집계, 장기결석 등재, 이름 열람, 검색, 프로필 저장.
- Edge Function `manage-accounts`: 로그인과 현재 계정 관리 권한을 검증한 뒤 Auth 초대와 업무 계정 연결을 수행합니다. 서비스 키는 서버 환경변수에서만 사용합니다.
- 화면: 기존 폼을 DB 저장에 연결했습니다. 운영 모드에는 시안 역할 전환·가상 데이터 초기화가 없습니다. 목록·카드·통계는 서버가 허용한 데이터로 구성하고, 보고 수치는 서버에서 다시 계산합니다.

현재 설계는 **한 Supabase 프로젝트에서 신도림지역 한 곳을 운영하는 구조**입니다. 여러 지역의 자료를 같은 프로젝트에서 서로 격리하는 다중 지역 SaaS 구조는 아닙니다.

## 1. 프로젝트 생성

선택한 조직은 `leejinho970715-star's Org`입니다. 새 프로젝트명 `management-system`, 서울 `ap-northeast-2`를 사용합니다. DB 비밀번호는 사용자가 Supabase 화면에서 직접 설정하고 보관합니다. 새 테이블 자동 공개는 끄고 자동 RLS는 켭니다. Data API는 켭니다.

이미 존재하는 다른 프로젝트나 중지된 프로젝트에 새 스키마를 임의로 적용하지 않습니다. 생성 후 실제 프로젝트 ID와 상태를 확인합니다.

## 2. SQL 적용

새 환경에 설치할 때는 `supabase/migrations/`의 파일을 파일명 순서대로 적용합니다. 공식 CLI로 생성한 파일이며, 순서는 스키마 → API → 기본 이벤트 함수 실행 권한 제한입니다. 새로운 DB를 대상으로 합니다. 가상 회원과 공유 로그인 비밀번호는 넣지 않습니다. 1~10구역, 신도림지역, 초기 운영 기준만 생성합니다. 현재 운영 프로젝트에는 이미 적용했으므로 다시 실행하지 않습니다.

연결 도구가 있으면 해당 프로젝트에 `apply_migration`으로 적용할 수 있습니다. CLI를 사용할 경우 먼저 현재 버전의 `supabase link --help`, `supabase db push --help`를 확인하고 프로젝트 연결 후 적용합니다. CLI 인증과 프로젝트 선택이 끝난 상태에서 실행해야 합니다.

```powershell
npx supabase link --project-ref 실제_프로젝트_ID
npx supabase db push
```

배포 후 SQL Editor에서 확인합니다.

```sql
select schemaname, tablename, rowsecurity
from pg_tables
where schemaname in ('private', 'finance')
order by schemaname, tablename;

select count(*) from private.districts; -- 10
select count(*) from private.members;   -- 최초에는 0
```

Data API 노출 스키마에는 `public`만 둡니다. `private`, `finance`를 추가하지 않습니다. 공개 RPC에는 `authenticated`의 필요한 실행 권한만 부여하며, `anon`과 브라우저 계정에는 테이블 직접 변경 권한이 없습니다. 내부의 `SECURITY DEFINER` 함수는 고정된 검색 경로, 현재 계정·소속·세션 검증과 컬렉션 허용 목록을 사용합니다. 공개 함수는 `SECURITY INVOKER`입니다.

스키마 적용 후 Supabase Security/Performance Advisor와 실제 SQL 조회를 수행합니다. 이미 적용된 마이그레이션을 고치는 대신, 변경이 필요하면 `supabase migration new 이름`으로 후속 마이그레이션을 만듭니다. `scripts/generate-schema.mjs`는 최초 스키마를 준비할 때만 사용하는 생성기입니다.

운영 적용 도구가 기록한 마이그레이션 버전에 맞춰 저장소 파일의 버전도 동기화했습니다. 기존 프로젝트에 같은 초기 스키마를 재적용하지 않습니다. 후속 변경 전에는 `supabase migration list`로 로컬/원격 이력을 확인합니다.

## 3. 최초 관리자와 지역장

첫 관리자는 공유 비밀번호를 코드에 넣어서 만들지 않습니다.

1. Supabase **Authentication → Users → Add user**에서 본인 이메일로 인증 사용자를 만듭니다. 비밀번호 입력·확인은 사용자가 직접 완료합니다.
2. SQL Editor에서 실제 이메일을 지정해 계정을 연결합니다. 아래 예시는 실제 주소로 바꾸어야 하며, 인증 사용자가 먼저 존재해야 합니다.

```sql
select public.app_provision_account(
  u.id,
  jsonb_build_object(
    'email', u.email,
    'role', 'admin',
    'district', '지역',
    'status', '활동'
  )
)
from auth.users u
where lower(u.email) = lower('본인의_실제_이메일');
```

3. 관리자로 사이트에 로그인합니다. 첫 지역장 계정도 같은 방식으로 연결하거나, SMTP 설정 후 계정 관리에서 `lead` 역할로 초대합니다. 초기에는 연결할 회원이 없으므로 관리자와 지역장은 회원 연결 없이 시작할 수 있습니다.
4. 지역장이 실제 회원을 등록합니다. 이후 구역장·업무 담당자를 해당 회원에 연결하여 초대합니다. 구역장은 담당 구역을 반드시 지정합니다.

`app_provision_account`는 서비스 역할/SQL 운영자 전용입니다. 일반 로그인 계정이 호출해 관리자 권한을 만들 수 없습니다. 마지막 활동 관리자의 비활성·역할 변경과 본인 계정의 권한 변경을 제한합니다. TF는 관리자 계정을 만들거나 관리자 역할을 부여할 수 없습니다.

계정 관리의 **직책 메뉴 제한 → 역할 + 직책 메뉴 기준**을 선택하면, 연결 회원의 시작일이 도래하고 회수되지 않은 사명 배정에서 직책 메뉴를 읽어 기본 역할 권한과 교집합을 적용합니다. 메뉴에는 `AT`, `VS`, `WR` 같은 그룹 또는 `ED-05` 같은 개별 화면 ID를 지정합니다. 적용 중인 직책이 없거나 회수되면 업무 권한을 주지 않으며, 본인 프로필은 사용할 수 있습니다. 관리자는 배정을 준비한 후 이 설정을 켤 수 있습니다. 관리자·시스템 TF는 운영 관리 예외이며, 이 예외가 회계·민감 상담의 기본 역할 제한을 해제하지는 않습니다. 직책 메뉴 제한이 켜진 사용자는 본인의 적용 직책을 변경해 스스로 권한을 늘릴 수 없습니다. 임기 종료 후 회수 방식은 기존 결정에 따라 수동이며 회수 즉시 서버 권한에 반영합니다.

## 4. Auth 및 메일 설정

운영 프로젝트의 Auth 설정에서 다음을 확인합니다. 저장소의 `supabase/config.toml`은 로컬 설정이며, 저장만으로 호스팅 프로젝트의 Auth 설정이 바뀌지는 않습니다.

- Site URL: `https://management-system-six-omega.vercel.app`
- Redirect URLs: Vercel 운영 주소와 `https://leejinho970715-star.github.io/management_system/**`. 로컬 검증이 필요하면 해당 로컬 주소도 추가합니다.
- 공개 회원 가입·익명 로그인: 사용하지 않습니다. 인증 사용자가 있어도 활동 중인 업무 계정이 연결되지 않으면 DB에 접근할 수 없습니다.
- 비밀번호 최소 길이: 12자 이상. 운영 메일 발송을 위한 SMTP와 발신 주소를 설정합니다. 메일 공급자 인증정보는 Supabase 서버 설정에만 저장합니다.
- 초대받은 사용자는 메일의 링크로 들어와 본인 비밀번호를 설정합니다. 초대·비밀번호 재설정 메일의 발송 성공은 실제 SMTP 연결 후 별도로 검증해야 합니다.

Auth 초대 메일과 DB 계정 연결은 서로 다른 서비스 작업입니다. 연결 과정이 부분 실패하면 인증 사용자를 자동으로 삭제하지 않습니다. 잘못된 기존 계정 삭제를 피하기 위해, 관리자가 해당 인증 사용자 ID와 업무 계정 연결을 확인하도록 오류를 표시합니다. 연결되지 않은 인증 사용자는 업무 자료를 볼 수 없습니다.

## 5. 계정 초대 서버 함수

`supabase/functions/manage-accounts/index.ts`를 같은 프로젝트에 배포합니다. 함수는 매 요청의 사용자 토큰을 Auth `getUser`로 검증하고 DB `app_authority`로 현재 세션·활동 상태·역할을 확인한 뒤에만 초대를 실행합니다. 비대칭 서명 키와 호환되지 않는 기존 게이트웨이 JWT 검사는 `verify_jwt=false`로 두며, 인증을 생략하는 설정이 아닙니다. 근거: [Supabase JWT 서명 키 안내](https://supabase.com/docs/guides/auth/signing-keys).

필요한 Supabase URL과 공개·서버 키는 Supabase Edge 런타임의 기본 환경변수에서 읽습니다. 현대식 키 사전(`SUPABASE_PUBLISHABLE_KEYS`/`SUPABASE_SECRET_KEYS`)과 기존 anon/service-role 환경변수를 지원합니다. `APP_AUTH_REDIRECT_URL`의 기본값은 실제 Vercel 운영 주소이며, 도메인을 추가하는 경우 `APP_ALLOWED_ORIGINS`도 설정합니다. 서비스 키를 `app/`, 공개 환경변수, Git 또는 채팅에 넣지 않습니다.

```powershell
# 해당 CLI 버전의 functions deploy --help를 먼저 확인합니다.
npx supabase functions deploy manage-accounts
```

## 6. 사이트 연결 및 배포

공개 연결 값만 Vercel 환경변수에 지정합니다.

```text
APP_SUPABASE_URL=https://실제프로젝트.supabase.co
APP_SUPABASE_PUBLISHABLE_KEY=sb_publishable_공개키
SITE_URL=https://management-system-six-omega.vercel.app
```

공개키는 Project Settings의 API Keys에서 확인합니다. 서비스/secret 키를 사용하면 빌드 스크립트가 거부합니다. GitHub Pages에도 같은 운영 DB를 연결하려면 공개 URL과 공개키를 `app/runtime-config.js`에 반영하거나 Actions의 해당 공개 설정을 빌드에 전달합니다. URL/공개키는 비밀번호가 아니지만, 데이터 접근은 반드시 로그인과 서버 권한 규칙으로 보호해야 합니다.

로컬에서는 `.env`에 값을 두고 아래처럼 실행합니다. `.env`는 Git에서 제외됩니다.

```powershell
npm ci
node --env-file=.env server.mjs 4174
```

운영 설정이 없으면 기존 가상 데이터 시안으로 실행됩니다. 운영 DB 오류가 발생했을 때 가상 데이터로 조용히 대체하지는 않습니다. 연결 오류를 표시합니다. 운영 설정이 활성화되면 실제 업무 자료를 `localStorage`의 시안 저장키에 저장하지 않습니다. 인증 세션 저장은 Supabase SDK가 관리합니다.

## 업무 처리와 계산

- 출석: 회원·연도·주차·예배별 1건. 입력 중복은 기존 행의 버전과 유일 인덱스로 제어합니다. 미입력은 결석을 생성하지 않습니다. 출석률은 활동·장기결석 회원 중 출석/온라인 비율입니다.
- 연속 결석: DB는 실제 주 시작일로 이전 연도까지 확인합니다. 미입력·사유결석·출석·온라인에서 연속이 끊깁니다. 기준 이상인 미종결 대상만 등재하고 동일 회원의 미종결 사건 중복을 막습니다.
- 전도: 현재 단계와 단계 이동 이력을 같은 트랜잭션에서 저장합니다. 접촉 등록·수정·삭제·복원 시 최근 접촉일을 다시 계산합니다.
- 교육: 총 회차를 넘는 참석 회차, 잘못된 교육 기간, 응시 시 점수 누락, 미응시에 점수 저장, 0~100점 범위를 벗어나는 점수를 차단합니다. 보고의 교육 참석은 교육일/기록일의 해당 주를 기준으로 계산합니다.
- 회계: 회원·구분·연월별 한 건, 양수 금액만 허용합니다. 합계는 삭제되지 않은 실제 납부 전체를 보존하며 회원의 비활성·삭제로 납부 금액이 사라지지 않습니다. 납부 인원·미납 인원·납부율의 대상은 현재 활동·장기결석 회원입니다. 지역장은 조회, 회계 역할은 입력·수정합니다. 구역장·관리자에게 회계 자료를 제공하지 않습니다.
- 주간보고: 서버가 입력 자료에서 수치를 다시 계산하여 제출 스냅샷을 만듭니다. 브라우저가 보낸 수치로 덮어쓰지 않습니다. 제출 이후 본문·수치 변경을 차단하고 지역장은 확인 상태만 변경합니다. 기능 보고는 작성자별로 분리합니다.
- 구역 이동: 회원 소속 변경과 이동 이력을 같은 트랜잭션으로 처리합니다. 회원 수정 폼에서 이력을 건너뛰는 소속 변경을 막습니다.
- 이월: 원본 ID/대상 회의의 유일 인덱스로 중복을 방지하고 진행 중·기한 경과 원본인지 서버에서 확인합니다.
- 민감 기록: 같은 역할이라도 다른 작성자의 민감 피드백·민감 심방 내용을 제공하지 않습니다. 지역장/회장과 원 작성자의 권한 및 회원 범위를 검증합니다. 구역장은 면담 결과 본문을 받지 않습니다.
- 이름: 목록은 서버에서 마스킹합니다. 실제 이름 검색도 서버에서 권한 범위를 적용하며, 전체 이름 열람 사유를 서버에 기록합니다. 수정용 기본 정보는 별도의 권한 검증·감사 기록 후 제공합니다.
- 동시 수정: 각 행의 `_version`이 서버 버전과 다르면 전체 변경을 거부합니다. 한 폼의 여러 행 변경은 모두 성공하거나 모두 취소됩니다.
- 삭제: 일반 업무 기록은 삭제 시각을 기록해 기본 조회에서 제외합니다. 기록 관리 → 삭제한 기록에서 복원할 수 있습니다. 구역·지역·계정은 비활성으로, 제출 보고·이동 이력·감사 로그는 보존합니다. 개인정보의 영구 파기는 보관 정책 확정 전 실행하지 않습니다.

SQL 테스트는 PGlite의 실제 PostgreSQL 엔진에 같은 마이그레이션과 업무 함수를 적용합니다. 브라우저 통합 테스트는 로컬 테스트용 Auth/REST 전송 계층과 실제 PostgreSQL 저장을 연결합니다. **Supabase 호스팅의 메일·게이트웨이·운영 배포까지 검증한 것으로 간주하지 않습니다.** 운영 프로젝트 생성 및 연결 후 같은 업무 흐름, 사용자별 권한과 Security Advisor를 다시 확인해야 합니다.

## 운영 범위와 남은 설정

현재 API는 계정이 볼 수 있는 해당 연도의 업무 자료를 초기 조회합니다. 한 지역의 기본 운영을 대상으로 하며, 대량 이력·대규모 동시 사용자에는 목록 페이지 처리와 집계 전용 API 확장을 별도로 수행해야 합니다. 원문에서 미확정인 회계 면제·분납, 보존기간과 익명화 승인, 자동 임기 회수, 외부 알림 채널은 임의로 정하지 않았습니다. 감사 로그에는 작업자·시각·대상·변경 항목·사유를 보존하며, 모든 변경 전 값을 복원하는 버전 보관 기능은 포함하지 않습니다. 백업·복구 정책과 정기 복구 테스트는 운영 DB 요금제·보관 정책을 정한 뒤 설정합니다.
